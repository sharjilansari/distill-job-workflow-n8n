Distill Job Agent

A daily pipeline that watches job boards through Distill, scores what it finds against your profile, tailors a resume per role, and submits the application. Designed around one hard limit: thirty webhook calls a month.

Superseded in part — read sources.md for how ingestion works now.

This document argues from a premise that turned out to be false: that Distill meters webhooks but not email. It does not. The free plan allows 30 alerts a month across email and webhook together — roughly one a day for an entire watchlist — and the webhook action is not available on the free plan at all. The “metered clock, unmetered pipe” split below, and the diagram that illustrates it, describe a channel that was never free.

Ingestion is now tiered. Tier 1 pulls job APIs that return structured JSON — free, uncapped, and needing no extraction call at all; that is the data path. Tier 2 is page diffing for sites with no API, and it is where Distill’s thirty alerts are best spent, as a canary on one high-priority search. Everything downstream of ingestion — the write-first rule for Tier 2, the status state machine, batching, the sheet as control panel — still holds exactly as described.

The constraint decides the design

Distill allows thirty webhook calls a month. That is the number every other decision follows from, so it is worth doing the arithmetic before drawing any boxes.

30 calls / month ÷ 1 per day = 30 days of cover 31-day months: short by one

One call a day consumes the entire allowance with nothing spare. Five monitors firing twice a day would exhaust the month in three days. A webhook cannot be the thing that carries your data.

So the webhook becomes a clock, not a pipe — and once you accept that, you may as well use a free clock. n8n's own Schedule Trigger costs nothing and never runs out. The thirty webhooks then become a bonus real-time lane for a single high-priority monitor: the saved search for the role you would drop everything for.

The data itself travels by the channel Distill does not meter.

Three ways out of Distill

Distill knows a page changed. Getting that knowledge into a workflow is the actual design question, and there are exactly three exits.

ChannelVolume limitData qualityRole here
Email action → Gmail Effectively unmetered Full diff text in the body primary pipe
Webhook action 30 / month Full diff, structured JSON one hot monitor
Dashboard scrape None Best, but brittle and login-gated last resort

Confirm the email-action limit on your own Distill plan before building ten monitors on the assumption. On every tier I have seen it is not metered the way webhook credits are — but check, because the whole shape of this design rests on it.

Getting the monitor right matters more than any of it

Roughly seventy percent of this system's reliability is decided in Distill, before n8n sees a byte. Four settings carry it:

  • Pre-filter at the URL. Not "LinkedIn jobs" — a saved search with the filters baked in. f_TPR=r86400 restricts to the last 24 hours, so the daily diff is naturally the day's new listings.
  • Select the results list, not the page. Otherwise the header, footer and sidebar ads all contribute to the diff.
  • Text mode, never HTML. These sites ship generated CSS class names that change between deploys; HTML mode fires constantly with no job change at all.
  • Strip the noise with regexes. Applicant counts and "2 hours ago" change without a new job existing. Skipping this is the single most common reason one of these pipelines re-processes the same forty jobs every morning forever.

Set the interval to 24 hours at a fixed time. Distill diffs against its last snapshot, so a daily check produces one change event containing everything posted that day — which is exactly the batch the workflow wants. A fifteen-minute interval would produce ninety-six fragments instead.

The daily pipeline

Two workflows, an hour apart. Each stage reads rows in one status and writes another; nothing reaches across.

StagereadswritesWhat it actually does
Ingest — raw_inbox Appends the payload verbatim before parsing anything
Parse raw_inbox — Splits the diff into job blocks, chunks them 20 at a time
Extract — — One model call per chunk, JSON schema enforced
Dedupe jobs — One sheet read, then an in-memory Set on URL and fingerprint
Hard filter — skipped Free, instant, typically removes 50–60%
Score — queued · review · skipped Scored against your profile, harsh rubric
Tailor queued — Resume rewrite + cover letter, rendered to PDF
Apply queued applied · manual · failed Per-ATS Playwright script, max 8 per run, one at a time

Write first, parse second

The first thing the workflow does with a payload is append it, untouched, to raw_inbox. Not parse it — append it.

The reason is the quota. A webhook fire is not replayable and you have thirty. A Gmail message can be re-read, but only if you have not marked it read prematurely. If the extraction call rate-limits at step four, the day's jobs must already be on disk. Everything downstream then reads from the sheet rather than from a transient payload.

Batch the model calls

Extraction sends twenty job blocks in one request and gets an array back. Sixty jobs is three calls, not sixty. Scoring runs one call per job — but only on the jobs that survived the free filters, which is where the 50–60% cut pays for itself.

Every call is schema-enforced by the provider — the exact mechanism differs between Claude, ChatGPT and Gemini, and the adapter absorbs that. The response is therefore guaranteed to parse, which is why the parsing nodes downstream are three lines each instead of defensive try-catch scaffolding.

Status is the backbone

One column in the jobs tab holds the entire control flow. Every stage selects rows in one status and moves them to another, which buys resumability for free: if a run dies halfway, tomorrow's picks up whatever is still open. There is no recovery logic anywhere in the system because none is needed.

The sheet is the database and the control panel

Four tabs. Google Sheets is genuinely the right choice here for longer than instinct suggests — being able to hand-edit a status column while you are still tuning the thing is worth a great deal, and Postgres only earns its place once jobs passes a few thousand rows.

TabGrainWhy it exists
raw_inbox One payload The safety net. Written before anything parses, trimmed to ~60 days.
jobs One posting The state machine. Deduped on canonical URL and fingerprint.
applications One attempt A job retried twice has two rows here and one in jobs.
run_log One run Trend data. Two consecutive zero raw_count rows means a monitor broke.

Two dedupe keys, because boards reuse neither consistently

The canonical URL strips tracking parameters and reduces a LinkedIn job to its numeric id, so …/jobs/view/senior-frontend-at-razorpay-4021938471?refId=abc and …/jobs/view/4021938471/?utm_source=share collapse to one key.

The fingerprint hashes company, title and city, which catches the same role reposted under a fresh URL — weekly on LinkedIn, constantly on Naukri.

Read the sheet once per run. Google Sheets allows roughly sixty writes a minute per user. Load the whole jobs tab into a Set in one call and filter in memory; a per-item lookup will exhaust the quota on any busy day and take the run down with it.

Applying: per-ATS scripts, not a browser agent

The submission service runs as a small HTTP server in its own container, not inside an n8n Code node. That separation buys four things: no execution timeout when a Workday form takes ninety seconds, the ability to test one handler in isolation, browser crashes that do not take down n8n, and session cookies that survive a restart on a volume.

Inside it, one script per applicant tracking system rather than one AI agent for everything. Greenhouse renders identical form markup for every company on the platform, so a single script covers hundreds of employers with stable selectors. An LLM driving a browser costs orders of magnitude more per application and fails unpredictably — worth keeping as the fallback for unrecognised domains, not as the default.

HandlerLocated byNotes
Greenhouse id + name Two form generations, both handled. Highest value to get right.
Lever name Most uniform of the three. Splits posting and apply pages.
Ashby visible label Client-rendered with churning class names; labels survive, CSS does not.
LinkedIn role + label manual by default
Anything else — Routed to you with the PDFs already generated.

On LinkedIn. It is the highest-volume source and it is also the account recruiters use to reach you. Automated applying is against the User Agreement and restrictions do happen. The handler ships refusing to submit unless you explicitly opt in, and even then only on single-step forms it can answer from your profile.

The alternative costs almost nothing: route it to manual, receive the tailored PDF on Telegram, tap through in forty seconds with no thinking. You keep the account and lose very little time.

Guardrails that ship on by default

  • Dry run. Fill every field, screenshot, stop before submitting. The row stays queued, so nothing is lost while you evaluate.
  • Eight per run, concurrency one, 45–120 seconds apart. Bursts get throttled far harder than steady traffic.
  • Screenshots before and after every submit, linked from the applications row. When a recruiter replies in three weeks you will want to know exactly what they read.
  • A failed application returns 200 with a result object. It is data, not an exception — a thrown error would abort the loop and strand every remaining job.

Build order

Not top to bottom. In slices that each work end to end, letting real data tell you what to fix next. The phases are a genuine sequence — each one's exit condition is the next one's precondition.

Getting installed is a separate, shorter job with its own click-by-click guide. What follows is what to do over the weeks after it runs, and every gate below is a line in .env rather than a code change.

  1. Prove the pipe one evening

    One monitor, one search, email to Gmail to a sheet. Disable every node after the raw append.

    Done when data arrives on its own two days running and the diff contains what you expect.

  2. Structure it one evening

    Enable parsing, extraction, dedupe and the hard filters. Run three days, then read the sheet by hand. This tuning pass is where you discover which noise regexes you actually need, and it is not skippable.

    Done when a morning's rows are jobs you would consider, with no repeats from yesterday.

  3. Score it half a day

    Enable scoring. Run a week in evaluation only — score everything, apply to nothing. If everything clusters at 80–90 the rubric is not biting; make it harsher rather than raising the threshold.

    Done when you agree with the model on nine of ten borderline calls.

  4. Tailor one day

    Generate resumes and cover letters. Still applying to nothing. Read ten end to end and verify nothing was invented — the prompt forbids it, but verify rather than trust.

    Done when ten resumes in a row are ones you would send unedited.

  5. Apply, narrowly two days

    Greenhouse only. Leave DRY_RUN=true for a day and read every screenshot. Then DRY_RUN=false with MAX_APPLICATIONS_PER_RUN=3, and watch each one.

    Done when ~20 submissions land with real confirmation pages in the after-screenshots.

  6. Widen

    Add Lever, then Ashby. Raise MAX_APPLICATIONS_PER_RUN toward eight. Leave LINKEDIN_AUTOSUBMIT=false.

    Done when you stop checking it every morning.

Failure modes

SymptomCauseFix
The same jobs re-extracted every morning Distill diffing on applicant counts and relative timestamps Regex filters in the monitor, not in n8n — stop the change being recorded at all
Sheets returns 429 Something is writing per item Batch every append; read the tab once per run
One source silently returns nothing Session expired; Distill is diffing a login wall Re-authenticate. Expect this every 2–4 weeks.
Every score is 85–95 The rubric, not the threshold Raising the cutoff moves the problem. Add explicit penalties instead.
submitted_unconfirmed Form went through, no confirmation text matched Check the after-screenshot; add that wording to the handler
Everything lands at manual Your sources are mostly consumer boards Expected. Add company career pages — they are overwhelmingly Greenhouse, Lever or Ashby underneath.

The one that hurts most is silence. A changed selector or an expired login, and for two weeks you assume nobody is hiring. Wire the canary: if raw_inbox gains no rows on two consecutive runs, alert yourself. Distill going quiet is a bug, not good news.

One file to configure, any model behind it

Three files hold everything a person needs to touch: .env for keys and switches, and two JSON files describing who they are. npm run setup validates all three, bakes the profile into the Code nodes, and builds the importable workflows.

Keys are never baked. The compose file sets NODE_FUNCTION_ALLOW_ENV, so Code nodes read the environment at run time. Rotating a key means editing one line and restarting — no rebuild, and no secret sitting inside a workflow file where it would end up in a backup or a screen share.

Switching AI is one line

All four model calls go through HTTP Request nodes that read $json._llm — the url, auth header and body that the shared library built for whichever provider is set. Changing LLM_PROVIDER touches no node and no prompt.

ProviderEndpointJSON enforced byReshaping needed
anthropic /v1/messages output_config.format none — schemas are authored in this dialect
openai /v1/chat/completions response_format strict strip minimum/maximum; strict mode rejects them
gemini :generateContent responseSchema OpenAPI dialect: ["string","null"] → nullable: true

That last column is the reason the abstraction sits in one library file rather than in three sets of prompts. Each schema is written once; the provider adapter reshapes it and normalises the response so every parser downstream is identical.

Effort is per-stage, not global. Extraction is mechanical transcription batched twenty at a time, so it runs at low effort and can point at a cheaper model. Scoring is judgement. The resume is read by a human, so it runs at high effort — that one call is where quality beats cost.

A health check that actually calls the model

npm run doctor checks config, reaches both services, and makes a real structured-output request to the configured provider. A wrong key or a model the account cannot use surfaces there, with the fix named, rather than at nine the next morning inside a workflow.

Why the build step. n8n stores Code-node bodies as a single JSON string full of escaped newlines. Editing that by hand is miserable and drifts from any copy you keep alongside it. So the .js files are the source of truth and setup injects them at build time — which also means the parsing logic can be tested outside n8n, and it is.

Playwright is already running for form submission, so page.pdf() renders the resume too. That replaces an entire external PDF service for free.
